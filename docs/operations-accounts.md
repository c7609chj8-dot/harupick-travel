# 관리자 로그인·회원관리 운영 절차

문서 버전: 0.2 / 운영매뉴얼 2일 차
작성·갱신일: 2026-11-26 (한국 시간)
대상: 본인에게 관리자 접근이 부여된 운영 점검 담당자
상위 문서: [운영매뉴얼](operations-manual.md) / 기록: [점검·인계 템플릿](operations-checklist.md)

## 시작 전

- [운영 관리자 화면](https://harupick-travel.vercel.app/admin.html)을 엽니다. 테스트·개인 복사본과 운영 주소를 구분합니다.
- 관리자 권한과 비밀번호는 별개입니다. 로그인은 본인 계정의 기존 이메일·비밀번호를 사용하며, 회원가입·이메일 인증만으로 관리자 권한이 생기지 않습니다.
- 담당자·연락 채널·실제 기록 보관 위치는 아직 미지정입니다. 필요한 접근이 없으면 미확인 사유와 인계 필요 사항을 기록합니다.
- 비밀번호·인증 코드·메일 링크·세션 정보는 점검 기록에 넣지 않습니다. 실제 회원 정보를 담은 화면·검색어는 공개 저장소에 올리지 않습니다.
- 이 절차의 회원관리는 조회 전용입니다. 회원 삭제·이용 제한·권한 부여·타인의 비밀번호 변경을 위한 절차가 아닙니다.

## 1. 관리자 로그인

| 순서 | 수행 | 정상 확인 | 다른 결과일 때 |
| --- | --- | --- | --- |
| 1 | 관리자 주소 접속 | 비로그인 상태면 ‘관리자 로그인이 필요합니다’와 로그인 링크 | 비로그인 상태에서 회원 정보가 보이면 긴급 인계 |
| 2 | ‘관리자 계정으로 로그인’ 선택 | 이메일·비밀번호 입력 화면 | 주소·네트워크 확인 후 실패 구역 기록 |
| 3 | 본인 계정 정보 입력 후 ‘로그인’ | 관리자 화면으로 복귀하거나 본인 닉네임 등록 단계 | 아래 로그인 오류표에 따라 처리 |
| 4 | ‘하루픽 닉네임 등록’이 나오면 본인 프로필용 닉네임 2~30자를 입력하고 ‘하루픽 회원 등록’ | 등록 성공 후 관리자 화면으로 복귀 | 오류를 기록. 통계 수를 맞추려고 다른 계정·프로필을 만들지 않음 |
| 5 | 관리자 화면의 현재 접속 계정·권한 확인 결과 점검 | 본인 계정이며 ‘관리자 권한 확인 완료’와 운영 콘솔 표시 | ‘관리자 권한이 없습니다’는 로그인 실패와 구분하여 인계 |
| 6 | 회원관리 목록 조회 확인 | 전체 수 또는 실제 0명 안내, 검색 폼 표시 | 조회 오류를 실제 0명으로 기록하지 않음 |

닉네임 등록은 인증된 본인 계정에 하루픽 프로필이 없을 때의 정상 단계입니다. 프로필 등록은 회원 데이터를 생성하므로 실제 점검에서는 본인의 필요한 최초 등록 때 수행합니다. 반복 점검용으로 실제 회원을 추가 생성하지 않습니다.

이미 콘솔이 열려 있으면 현재 계정부터 확인합니다. 계정이 다르면 로그아웃 후 본인 계정으로 로그인합니다. ‘권한이 없습니다’ 화면에는 콘솔의 로그아웃 버튼이 없으므로 해당 화면의 로그인 링크에서 본인 관리자 계정으로 다시 로그인할 수 있습니다.

탭으로 돌아오거나 인증 상태가 바뀌면 권한을 다시 확인합니다. 권한 거부를 확인하면 콘솔과 회원 데이터가 제거되어야 합니다. 화면의 권한 확인 시각은 서버 데이터 집계 시각이나 권한이 영구 보장된다는 뜻이 아닙니다.

## 2. 로그인·접근 오류 대응표

| 표시·상황 | 의미·확인 | 운영 담당자의 조치 |
| --- | --- | --- |
| 이메일 또는 비밀번호를 확인해 주세요 | 계정 정보가 거절됨. 이메일 존재 여부·단순 오타를 이 메시지만으로 단정할 수 없음 | 입력 주소·키보드 상태를 본인이 확인. 반복 추측 대신 본인 복구 절차 이용 |
| 이메일 인증을 먼저 완료해 주세요 | 이메일 인증이 확인되지 않음 | 본인 받은 메일함·스팸함 확인. 관리자 권한 부여와 다른 단계임을 안내 |
| 하루픽 닉네임 등록 | 인증된 계정에 하루픽 프로필이 없음 | 본인에게 필요한 최초 프로필 등록 진행 |
| 관리자 로그인이 필요합니다 | 로그인 세션이 없거나 다시 로그인해야 함 | 관리자 로그인 링크로 본인 계정 로그인 |
| 관리자 권한이 없습니다 | 현재 계정·인증·권한·계정 상태·세션의 관리자 접근 검사 거부 | 현재 계정 확인 후 기술 담당자에게 인계. 회원의 ‘이용 가능’ 배지만으로 권한을 판단하지 않음 |
| 권한을 확인하지 못했습니다 | 접근 확인 요청 실패. 권한이 없다고 확정된 상태와 다름 | 연결 확인 후 ‘다시 확인’ 1회. 계속 실패하면 시각·구역·문구 기록 |
| 메일 발송이 일시적으로 제한됐어요 / 요청이 많아요 | 발송·요청 제한 응답 | 반복 요청 중단 후 안내에 따라 나중에 재시도. 지속되면 기술 담당 인계 |
| 현재 메일 발송 설정에서 허용되지 않는 이메일입니다 | 시범 운영 메일 설정에 따른 거절 | 지원 범위를 기술 담당자에게 확인. 설정을 임의로 넓히지 않음 |
| 서버에 연결할 수 없어요 | 네트워크·인증 서버 요청 실패 가능 | 연결과 운영 주소 확인 후 1회 재확인. 실제 0명·계정 삭제로 해석하지 않음 |
| 요청을 처리하지 못했어요 | 구체적으로 분류되지 않은 실패 | 오류 문구·발생 구역·시각을 기록하고 기술 담당에게 인계 |

이 표는 가능한 원인과 첫 조치입니다. 화면 문구만으로 비밀번호 노출·계정 삭제·권한 회수 원인을 확정하지 않습니다. 기술 담당자가 필요한 서버 기록과 현재 권한을 확인합니다.

## 3. 본인 비밀번호 재설정

이 절차는 화면·소스 구현을 확인한 안내입니다. 이번 문서 작성에서 실제 운영 메일 수신·복구 링크 완료·비밀번호 변경은 실행하지 않았습니다.

1. 로그인 화면의 ‘비밀번호 재설정’ 또는 [재설정 화면](https://harupick-travel.vercel.app/reset-password.html)을 엽니다.
2. 본인 가입 이메일을 입력하고 ‘재설정 링크 받기’를 누릅니다.
3. ‘등록된 이메일이라면 재설정 안내가 발송됩니다’ 안내를 확인합니다. 이 문구만으로 해당 이메일의 가입 여부나 실제 메일 수신을 확인한 것은 아닙니다.
4. 본인 받은 메일함과 스팸함을 확인합니다. 링크 요청에 사용한 브라우저에서 본인이 받은 최신 링크를 엽니다. 링크를 다른 사람에게 전달하거나 기록에 붙이지 않습니다.
5. 유효한 복구 세션이면 ‘새 비밀번호를 입력해 주세요’와 새 비밀번호·확인 입력칸이 나옵니다. 본인이 화면의 8~72자 기준과 확인값에 맞게 입력하고 ‘새 비밀번호 저장’을 누릅니다. 서버의 비밀번호 정책에 따라 추가 거절될 수 있습니다.
6. 변경 성공 안내를 확인하고 새 비밀번호로 로그인한 뒤 관리자 주소에서 권한을 다시 확인합니다. 로그인 상태를 다시 확인하라는 안내가 나오면 현재 세션도 확인합니다.

| 예외 | 대응 |
| --- | --- |
| 링크가 만료됐거나 다른 브라우저에서 열렸다는 안내 | 요청한 브라우저인지 확인하고 본인이 새 링크를 요청. 반복 발송 제한에 주의 |
| 비밀번호가 일치하지 않음 | 두 입력값을 본인이 다시 확인 |
| 더 안전한 비밀번호 / 기존 비밀번호와 다른 값 안내 | 화면·서버가 요구한 기준에 맞춰 본인이 수정 |
| 메일이 오지 않음 | 받은 메일함·스팸함·입력 주소 확인 후 발송 제한 여부를 구분. 즉시 성공으로 기록하지 않고 지속 시 기술 담당 인계 |

동일한 공유 인증 계정을 다른 서비스에서도 사용하면 비밀번호 변경이 그 서비스의 로그인에도 영향을 줄 수 있습니다. 운영 담당자는 다른 회원에게 비밀번호를 받아 대신 입력하거나, 그 회원의 복구 링크를 열지 않습니다.

회원가입·이메일 인증 확인도 실제 메일 전달과 링크 완료까지 확인해야 운영 성공으로 기록할 수 있습니다. 이 문서의 자동·모의 검증 결과를 실제 메일 수신 성공으로 바꾸어 기록하지 않습니다.

## 4. 회원 검색·필터·정렬

회원관리 구역으로 이동합니다. 이 화면에는 하루픽 프로필이 연결된 계정만 표시되므로, 목록에 없다는 이유만으로 공유 Auth 계정 자체가 없다고 단정하지 않습니다.

| 순서 | 수행 | 확인 |
| --- | --- | --- |
| 1 | 현재 ‘적용한 조건’과 전체/검색 결과 수 확인 | 이미 적용된 조건과 입력 중인 값을 구분 |
| 2 | 닉네임 또는 이메일 검색어 입력 | 부분 검색. %와 _는 일반 문자이며 검색어는 최대 100자 |
| 3 | 계정 상태 선택 | 전체·이용 가능·이메일 미인증·이용 제한·삭제된 계정 중 선택 |
| 4 | 필요하면 가입 시작일·종료일 입력 | 하루픽 프로필 등록일의 한국 날짜. 각각 생략 가능, 양 끝 날짜 포함 |
| 5 | 가입일 최신순 또는 오래된 순 선택 | 정렬만 변경하면 전체 수 자체를 줄이는 조건은 아님 |
| 6 | ‘검색·조건 적용’ 또는 검색 입력칸 Enter | 첫 페이지에서 새 조건으로 조회 |
| 7 | ‘적용한 조건’, 결과 수, 날짜·상태·정렬 확인 | 운영 데이터에 따라 실제 0건도 정상 가능. 오류 메시지와 구분 |
| 8 | 이전·다음으로 페이지 이동 | 한 페이지 20명, 같은 적용 조건과 정렬 유지 |

- 입력칸만 바꾸면 기존 목록은 유지되고 미적용 안내가 표시됩니다. 변경한 조건을 조회하려면 반드시 적용합니다.
- 회원관리 오른쪽의 ‘새로고침’, 페이지 이동, ‘목록 다시 불러오기’는 마지막으로 적용한 조건을 사용합니다. 입력 중인 조건으로 바뀌는 동작이 아닙니다.
- ‘초기화’는 검색어·상태·기간·정렬·입력 오류를 기본값으로 되돌리고 첫 페이지를 조회합니다.
- 시작일이 종료일보다 늦으면 오류를 표시하고 요청하지 않습니다. 기존 결과와 적용 조건은 유지됩니다. 날짜를 고친 뒤 다시 적용합니다.

### 조회 예시

| 목적 | 조건 예시 | 확인할 점 |
| --- | --- | --- |
| 미인증 회원 찾기 | 상태: 이메일 미인증, 나머지 제한 없음 | 결과 행이 미인증인지 확인. 관리자가 인증 완료로 바꾸는 기능은 없음 |
| 특정 기간 가입 회원 찾기 | 시작일 2026-11-01, 종료일 2026-11-30 | 프로필 등록일 기준이며 운영 데이터에 따라 건수는 다름 |
| 이전 가입부터 검토 | 정렬: 가입일 오래된 순 | 결과·표 설명이 오래된 순으로 바뀌는지 확인 |
| 검색 조건 때문에 안 보이는지 확인 | 초기화 후 필요한 검색만 다시 적용 | 필터 제거 후에도 없으면 아래 ‘회원 없음’ 판단 기준 적용 |

## 5. 상태와 숫자 해석

| 표시 | 의미 |
| --- | --- |
| 이용 가능 | 삭제·이용 제한 상태가 아니고 이메일 인증 완료. 관리자 권한을 의미하지 않음 |
| 이메일 미인증 | 삭제·이용 제한 상태가 아니고 이메일 인증 미완료 |
| 이용 제한 | 삭제 상태가 아니고 서버의 제한 기간 적용 중 |
| 삭제된 계정 | 인증 계정이 삭제 상태이고 연결된 하루픽 프로필이 남아 있는 경우. 완전히 삭제된 모든 계정을 보여주는 탈퇴 이력은 아님 |
| 확인 필요 | 화면에서 상태를 해석할 수 없는 경우. 실제 API 응답 검증 실패는 조회 오류로 표시될 수도 있음 |
| 전체 N명 / 검색 결과 N명 | 현재 목록 또는 필터 결과. 대시보드 가입 완료 회원 수와 같아야 하는 숫자가 아님 |
| 21–23번째 회원 표시 | 현재 조회 조건 안에서의 표시 순번. 전체 서비스의 고정 회원 번호가 아님 |

상태 우선순위는 삭제 → 이용 제한 → 이메일 미인증 → 이용 가능입니다. 본 화면에서 상태를 수정하지 않습니다.

## 6. 상세 조회와 목록 복귀

1. 필요한 회원 행에서 ‘상세 보기’를 누릅니다. 모바일에서는 표 안을 좌우로 밀어 버튼을 찾을 수 있습니다.
2. 상세 상단의 닉네임·선택 페이지를 확인하고 계정 정보의 회원 ID·이메일·상태로 대상이 맞는지 확인합니다. 닉네임만으로 서로 다른 회원을 같은 계정으로 간주하지 않습니다.
3. ‘등록·인증 시각’에서 하루픽 가입·프로필 수정·이메일 인증·최근 계정 로그인을 구분합니다. 모두 한국 시간입니다.
4. 이메일 없음·미인증·기록 없음 안내는 각각의 값이 없다는 의미입니다. 최근 계정 로그인은 공유 계정의 다른 서비스 로그인도 포함할 수 있어 하루픽 방문 시각으로 해석하지 않습니다.
5. 상단 ‘상세 닫기’, 하단 ‘회원 목록으로 돌아가기’, 또는 상세 영역에서 Esc를 사용합니다.
6. 같은 회원 버튼에 포커스가 돌아오고 필터·정렬·현재 페이지가 유지되는지 확인합니다. 원래 버튼이 없으면 검색 입력칸으로 복귀할 수 있습니다.

긴 이메일·회원 ID는 줄바꿈해 전체를 표시합니다. 상세는 비모달 영역이므로 포커스를 가두지 않습니다. 상세 밖의 검색칸에서 Esc를 눌러도 상세 닫기로 처리하지 않습니다.

## 7. 회원 조회 예외 대응

| 화면 결과 | 판단 | 조치 |
| --- | --- | --- |
| 아직 등록된 회원이 없음 / 조건에 맞는 회원 없음 | 정상 응답의 실제 0건 | 적용 조건 확인, 필요한 경우 초기화. 오류로 임의 분류하거나 회원을 만들어 채우지 않음 |
| 회원 목록을 불러오지 못함 | 조회 오류. 0건과 다름 | 연결 확인 후 ‘목록 다시 불러오기’ 1회. 마지막 적용 조건을 기준으로 재조회됨 |
| 회원 정보를 불러오지 못함 | 상세 조회 오류 | ‘상세 다시 불러오기’ 1회, 지속 시 목록 복귀·기록·인계 |
| 이 회원은 삭제되었거나 하루픽에 등록되어 있지 않음 | 상세가 존재하지 않음. 원인 확정은 아님 | 목록 복귀 후 필요시 새로고침. 목록·상세가 달랐던 시각을 기록하고 지속 시 기술 담당 확인 |
| 조회 중 권한 없음·로그인 필요로 이동 | 접근 검사 거부 또는 세션 문제 | 콘솔·상세·검색어·적용 조건이 제거되는지 확인. 로그인/접근 오류표로 대응 |
| 조건을 바꿨는데 이전 결과가 보임 | 미적용 입력일 수 있음 | ‘적용한 조건’과 미적용 안내 확인 후 검색·조건 적용 |
| 회원 수가 대시보드와 다름 | 모집단 차이일 수 있음 | 가입 완료 기준과 현재 필터부터 확인. 숫자 일치 목적으로 데이터 변경하지 않음 |

실제 권한 회수·계정 제한·비밀번호 변경으로 운영 장애를 만들어 시험하지 않습니다. 오류·권한 해제 재현은 별도 검증 환경에서 하거나 실제 발생한 상황의 근거를 확인합니다.

## 8. 작업 종료·인계

- 콘솔의 ‘로그아웃’을 누른 뒤 로그인 안내로 돌아오고 회원 목록·상세 값·검색어·적용 조건이 남지 않는지 확인합니다.
- 이 로그아웃은 현재 브라우저의 로그인 세션을 종료하는 동작입니다. 다른 모든 기기의 세션까지 종료했다고 기록하지 않습니다.
- 본인의 브라우저 여행 복사본이 남는 것은 별도 저장 방식입니다. 회원관리 조회 데이터가 남는 경우와 구분합니다.
- 점검 결과는 정상·이상·미확인과 근거·시각·다음 조치·담당을 기록합니다. 실제 회원 이메일·복구 링크·비밀번호를 기록에 넣지 않습니다.
- 개인정보 비노출 실패는 [운영매뉴얼의 이상 분류](operations-manual.md)에 따라 긴급 인계합니다.

## 작성 근거와 검증 범위

- 화면·동작은 login.html, reset-password.html, auth-ui.js, auth-client.js, admin.js, admin-access.js, admin-members-ui.js와 대조했습니다.
- 이번 작성에서 인증·접근·회원 API·SDK/컨트롤러 통합 자동 테스트 27개를 재실행해 통과했습니다. 모의 응답을 사용하는 자동 검증이며 실제 운영 로그인 성공의 증거가 아닙니다.
- 문서 4개·로컬 링크 45개와 이모지 미사용 검사, 사이트 정적 연결 검사를 통과했습니다. 운영 점검 명령도 페이지·자산 68개 정상 응답과 보호 RPC 7개 익명 접근 차단으로 PASS했습니다. 이는 실제 관리자 로그인·메일 수신 확인과 별개입니다.
- 이전 모의 브라우저에서 로그인·프로필 등록·관리자 복귀, 회원 필터·상세·목록 복귀·오류·권한 거부·로그아웃을 검증했습니다. 근거는 아래 개발 검증 문서에 있습니다.
- 실제 관리자 계정으로 운영 로그인, 운영 메일 수신·인증 링크 완료·비밀번호 변경은 이번 문서 작성에서 실행하지 않았습니다. 운영에서 확인한 날짜·계정 소유자의 확인 결과가 생기면 별도 기록합니다.
- 담당 실명·연락 채널·기록 보관 위치는 계속 미지정입니다. 이 문서 작성으로 계정·권한·인증 설정을 변경하지 않았습니다.

## 2026-11-26 재설정 화면 보완

- 재설정 메일은 공식 운영 주소에서 요청합니다. 다른 출처에서 요청하면 화면의 공식 주소 링크로 이동한 뒤 진행합니다. 요청 주소와 메일 복귀 주소가 다르면 PKCE 검증에 필요한 브라우저 저장값을 사용할 수 없습니다.
- 메일 앱이 다른 브라우저를 열면 최신 메일 링크 주소를 복사해 요청에 사용한 브라우저 주소창에서 엽니다. 이미 소비됐거나 만료된 링크는 다시 사용할 수 없으므로 발송 제한이 해제된 뒤 새 링크를 요청합니다. 비밀 링크를 채팅·운영 기록에 붙이지 않습니다.
- 복구 인증이 확인된 동일 탭에서는 새로고침 후에도 새 비밀번호 입력을 이어갈 수 있도록 사용자 ID만 sessionStorage에 보존합니다. 화면 재진입·저장 전에 서버에서 현재 사용자를 확인하며 다른 사용자에게 이 상태를 적용하지 않습니다. 탭 저장 공간이 차단되면 새로고침 후 유지가 불가능할 수 있습니다.
- 저장 성공·로그아웃·다른 계정 전환·복구 확인 실패 시 복구 문맥을 정리합니다. 비밀번호·메일 코드·복구 토큰을 이 문맥에 추가 저장하지 않습니다. 실제 인증 세션 저장은 기존 SDK 방식입니다.
- 발송 제한 안내는 프런트엔드 수정으로 해제되지 않습니다. 연속 요청을 멈추고 제한 해제 후 재시도합니다. 공유 프로젝트의 다른 서비스·메일 설정은 이 수정에서 변경하지 않았습니다.
- 검증: 전체 자동 테스트 84개 통과. 추가 복구 테스트 5개는 실제 SDK와 모의 Auth 응답으로 PKCE 콜백·동일 사용자 새로고침·일반 로그인/다른 사용자 차단·서버 저장 거절 후 재시도·로그아웃 상태 정리를 검증했습니다. 실제 메일 수신과 실제 비밀번호 변경은 수행하지 않았습니다.

### 메일 인증 후 요청 화면에 머무는 경우

- PASSWORD_RECOVERY 이벤트가 화면 최초 로딩 이후 또는 다른 탭에서 도착해도 서버에서 본인 사용자를 확인한 뒤 이메일 요청 폼을 숨기고 새 비밀번호 폼을 표시합니다. 탭 복귀 시에도 확인합니다. 인증 이벤트 안에서 SDK 요청을 직접 기다리지 않고 다음 작업으로 넘겨 인증 잠금을 피합니다.
- 메일 링크를 연 뒤 원래 화면에 머문다면 새 메일을 반복 요청하기 전에 ‘메일 인증 후 계속’을 누릅니다. 이 버튼은 기존 복구 상태를 검증하며 인증 없이 새 비밀번호 화면을 허용하지 않습니다.
- 실제 설정 읽기 점검에서 공식 reset-password.html 복귀 주소 허용 및 기본 ConfirmationURL 메일 템플릿을 확인했습니다. 공유 프로젝트 설정은 변경하지 않았습니다.
- 추가 검증: 늦은 인증 이벤트에 따른 실제 auth-ui 폼 숨김/표시·로그아웃 초기화, SDK 잠금 밖의 상태 조회, 지연 응답과 계정 전환 차단을 모의 환경에서 확인했습니다. 실제 계정의 비밀번호 변경 완료는 별도 본인 확인이 필요합니다.
