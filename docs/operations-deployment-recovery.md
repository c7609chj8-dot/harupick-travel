## 정상 배포 확인

1. 저장소에서 변경 범위·커밋·브랜치를 확인합니다. 아래 읽기·검증 명령은 저장소 루트에서 실행합니다.

```powershell
git status --short
git branch --show-current
git log -3 --oneline
node scripts/check-site.mjs
node --test tests/*.test.mjs
```

2. 문서만 변경했다면 문서 링크·표현·차이를 검증합니다. 제품 코드 변경이면 관련 자동 테스트와 필요한 화면·API 검증을 수행합니다. 검사 실패 상태로 배포 완료를 선언하지 않습니다.
3. 검토한 변경만 GitHub main에 반영합니다. Vercel의 해당 프로젝트 Deployments에서 저장소·main·정확한 커밋·production을 대조합니다.
4. 배포가 READY가 될 때까지 상태를 확인합니다. ERROR·CANCELED·BLOCKED는 완료가 아닙니다. 해당 배포의 Build Logs에서 최초 오류를 확인하고, 업로드·설정·파일 경로·검사 오류를 구분합니다.
5. 운영 도메인이 의도한 배포에 연결됐는지 확인합니다. 최근 생성된 READY 배포가 운영 별칭을 받았다고 가정하지 않습니다.
6. 공개 운영 주소를 점검합니다.

```powershell
node scripts/smoke-production.mjs
```

7. 변경 영역을 실제 화면에서 확인합니다. 로그인·회원·일정·통계 변경은 권한 있는 본인 계정으로 필요한 흐름을 점검하고, 실제 데이터 변경은 필요한 업무에 한정합니다. 실제 메일 수신과 복구 링크 완료는 별도 확인 항목입니다.
8. 커밋·배포 ID·환경·운영 별칭·한국 시간·실행 명령·종료 코드·PASS/실패·미확인 범위를 기록합니다.

운영 점검 스크립트는 공개 페이지·자산 HTTP 상태, HTML/JavaScript MIME, 보호 RPC의 익명 401/403, 공개 이메일 인증 설정을 검사합니다. 응답 200만으로 화면 기능·현재 파일 내용·실제 로그인·메일·데이터 정합성까지 검증하지 않습니다. 검사 기준은 로컬 소스와 auth-config.js를 사용하므로 다른 커밋의 배포와 비교할 때 추가·삭제된 파일 차이도 고려합니다.

배포 고유 주소나 preview가 Vercel 로그인·401·403을 반환하면 플랫폼 Deployment Protection인지 먼저 구분합니다. 승인된 Vercel 접근으로 확인하며 보호 설정을 해제해 통과시키지 않습니다. 플랫폼 로그인 HTML의 200도 앱 정상 증거가 아닙니다. 보호 RPC의 익명 401/403은 정상 차단이며 공개 운영 페이지의 차단과 구분합니다.

## 장애 초기 대응과 진단

1. 발생 시각·화면 경로·영향 기능·오류 상태·마지막 정상 확인·최근 커밋/설정 변경을 기록합니다. 비밀값·실제 회원 정보·복구 링크를 공개 기록에 넣지 않습니다.
2. 다른 새 접속 또는 재조회로 한 번 확인하고 범위를 나눕니다. 브라우저 데이터 삭제·계정 삭제·반복 저장으로 원인을 찾지 않습니다. 저장 결과가 불명확하면 [일정 결과 불명 대응](operations-trips-audit-dashboard.md)을 따릅니다.
3. 배포 상태와 운영 별칭을 확인합니다. 새 배포 실패와 기존 운영 서비스 중단은 별개일 수 있습니다.
4. 아래 표에 따라 프런트엔드·인증·DB·기기 문제를 구분하고 해당 담당자에게 인계합니다. 서비스 제공자의 상태 페이지도 참고하되 개별 프로젝트 장애가 없다는 증거로 사용하지 않습니다.

| 증상·사례 | 우선 확인 | 조치·중단 기준 |
| --- | --- | --- |
| 새 배포 ERROR, 운영 화면은 정상 | 실패 커밋·Build Logs·현재 운영 배포 | 실패 원인을 수정해 재검증. 정상 운영을 임의 롤백하지 않음 |
| 페이지·자산 404 또는 JS MIME 오류 | 파일 경로·대소문자·실제 커밋·별칭 | 누락 파일·경로 수정. 회귀가 배포 원인이라면 검증된 이전 배포 검토 |
| 화면은 열리지만 관리자 조회 실패 | 계정·세션·관리자 권한, 실패 RPC·HTTP 상태 | [계정 절차](operations-accounts.md) 적용. 조회를 위해 접근 제어·이메일 인증을 해제하지 않음 |
| 여러 보호 API 연결 실패·5xx | Supabase 프로젝트 상태·관련 Auth/Postgres/API 로그·최근 DB 변경 | 시각·오류 코드로 상관관계 확인. 프런트엔드만 되돌려 해결된다고 가정하지 않음 |
| 메일 발송 안내 뒤 미수신 | 실제 수신 여부·정크함·만료·Auth 로그·발송 제한 | 반복 발송을 멈추고 원인 확인. 실제 수신 전 완료로 기록하지 않음 |
| 일부 기기에서 일정 누락 | 로그인 계정·브라우저/서버 저장 구분·저장 공간 | 브라우저 초기화 전에 사용자 파일·서버 복사 가능 여부 확인 |
| 통계 0·이력 없음 | 조회 완료/오류·조건·기간·집계 시각 | [통계 정의와 이력 범위](operations-trips-audit-dashboard.md) 확인. 데이터를 임의 보정하지 않음 |
| 비로그인 보호 API 성공·개인정보 노출 | 노출 경로·발생 시각·최소 상태 증거 | 추가 개인정보 조회 중단. 기술 담당·책임자에게 긴급 인계, 영향과 차단 방안을 우선 판단 |

로그는 실패한 기능이 실행되는 곳에서 찾습니다. 정적 Vercel 사이트의 Runtime Logs에 Supabase RPC·Auth 내부 오류가 모두 나타나는 것은 아닙니다. 개인정보가 포함된 전체 로그를 공개 저장소에 첨부하지 않습니다.

## 프런트엔드 긴급 되돌리기

대상은 새 프런트엔드 배포로 생긴 회귀이며, 정상 검증된 이전 배포가 현재 DB·API와 호환될 때입니다. DB 장애·잘못 저장된 회원 데이터·유출된 비밀값은 배포 롤백만으로 복구되지 않습니다.

1. 현재 운영 커밋·배포 ID·별칭과 장애 증거를 기록합니다. 다른 배포·promotion·rollback 작업이 진행 중인지 담당자 간 확인합니다.
2. 이전 배포의 커밋·정상 확인 근거·현재 서버 API 호환성을 검토합니다. 단순히 직전 커밋이라는 이유로 선택하지 않습니다. 최근 DB 변경이 있으면 호환성 확인 전 이전 코드를 운영에 연결하지 않습니다.
3. Vercel 프로젝트의 Production Deployment에서 Instant Rollback을 열고 실제 선택 가능한 대상·권한을 확인합니다. 공식 문서상 Hobby는 직전 배포, Pro/Enterprise는 적격 배포 중 선택할 수 있으므로 현 요금제·화면의 대상 목록을 기준으로 합니다.
4. 검토한 대상에 한해 롤백을 실행합니다. 완료 상태와 운영 별칭이 대상 배포로 이동했는지 확인한 뒤 공개 점검·영향 기능을 재검증합니다. 요청 접수·시간 초과만으로 실패나 성공을 단정해 재실행하지 않습니다.
5. 롤백은 GitHub main을 되돌리지 않습니다. main과 현재 운영 커밋이 다른 상태를 기록합니다. Vercel은 롤백 후 새 production 배포의 운영 도메인 자동 연결을 멈추므로 push만으로 정상 자동 배포가 복구된다고 가정하지 않습니다.
6. 원인을 고친 커밋을 검증하고 정상 production 배포를 준비합니다. Vercel의 정상 배포 promotion 또는 Undo Rollback 절차로 의도한 배포를 연결하고 자동 연결 재개 여부를 확인합니다. 해로운 원래 배포를 그대로 Undo하지 않습니다.
7. 운영 별칭·커밋·READY·공개 점검·영향 기능을 확인하고 임시 복구와 근본 수정의 완료 여부를 따로 기록합니다.

CLI를 사용한다면 공식 rollback/promote 문서와 현재 도움말을 확인하고 팀·프로젝트·대상 배포를 명시적으로 대조합니다. 이 문서 작성에서는 CLI 롤백을 실행하거나 인증 정보를 수집하지 않았습니다.

## Git 변경 되돌리기와 수정 배포

- Git의 revert는 원인 변경을 반대로 적용하는 새 커밋입니다. 운영 도메인을 즉시 이전 배포로 옮기는 Vercel 롤백과 효과·시점이 다릅니다.
- 기술 담당자는 문제 커밋과 후속 의존 변경을 확인하고 codex/ 접두사의 작업 브랜치에서 수정 또는 revert 결과를 검토합니다. 커밋 범위·merge commit의 부모·충돌은 개별 판단하며 무조건 직전 커밋을 취소하지 않습니다.
- 미커밋 작업을 보존하고 diff와 정적 검사·관련 테스트를 확인한 후 main에 반영합니다. 공유 main에 reset --hard·강제 push로 이력을 덮어쓰는 방식은 사용하지 않습니다.
- main 반영 후 새 production 배포의 커밋·READY·별칭을 확인합니다. 앞서 Vercel 롤백을 했다면 자동 연결 중단 상태를 먼저 확인하고 정상 배포 promotion을 마무리합니다.
- 서버 마이그레이션·Auth 설정·데이터 수정은 Git revert에 포함되지 않습니다. 별도의 검토된 조치와 검증이 필요합니다.

## 데이터·인증 복구와 백업 확인

| 대상 | 사용할 수 있는 근거·수단 | 경계 |
| --- | --- | --- |
| 제목·날짜·보관 상태의 잘못된 변경 | 최신 상세·버전과 감사 전후 값을 대조해 필요한 값 재입력 | 다른 후속 변경을 덮어쓰지 않음. 전체 일정 본문 복원 수단이 아님 |
| 브라우저 일정 | 사용자가 보유한 하루픽 JSON 백업 가져오기 | 현재 구현은 같은 일정 ID가 이미 있으면 건너뜀. 서버·회원·Auth 백업이 아님 |
| 서버 데이터 손실 | 실제 존재하고 검증 가능한 DB 백업 또는 PITR 후보 | 프로젝트의 요금제·활성 여부·보존 구간·복구 가능 시점 미확인 |
| Auth·프로젝트 설정 문제 | 변경 기록·현재 설정과 정상 기준 비교 | 공유 서비스 영향 확인. 배포·Git만 되돌려서는 복구되지 않음 |

1. 데이터 손실 의심 시 영향 범위·마지막 정상 시각·이후 정상 쓰기를 확인하고 불필요한 쓰기를 멈춥니다. 실제 쓰기 중단 방법·다른 서비스 범위는 기술 담당자가 결정합니다.
2. Supabase Dashboard의 Database > Backups에서 실제 백업 존재·성공 상태·시각·보존 범위와 PITR 활성 여부를 확인합니다. 미확인 항목을 자동 백업 보장으로 표현하지 않습니다. 백업 이용 가능 범위는 요금제·설정에 따라 다릅니다.
3. 복구 후보 시각 이후 유실될 정상 변경, Auth·다른 서비스 영향, 보존할 현재 데이터, 복구 범위·실행자·접근 권한·재검증·복구 실패 시 대응을 구체적으로 기록합니다.
4. 공유 프로젝트 전체 복원을 일상 조치로 실행하지 않습니다. 실제 복원이 필요하면 다른 서비스 담당자와 범위를 조율하고 복구 계획을 확정합니다. 가능하면 격리된 대상에서 복원 결과와 필요한 데이터·권한·스키마를 먼저 검증하고 필요한 범위만 복구하는 방안을 검토합니다.
5. 복원 방법에 따라 별도 처리해야 하는 설정·Storage 객체·역할 인증 정보 등을 공식 문서로 확인합니다. DB 백업은 Storage 파일 본문을 포함하지 않습니다. 저장소 스키마 참고·감사 요약·브라우저 JSON을 프로젝트 전체 복원본으로 사용하지 않습니다.
6. 실제 복구 후 데이터 정합성·관리자 및 일반 회원 권한·익명 차단·Auth·연결 설정·영향받은 다른 서비스까지 확인합니다. 증거와 잔여 손실을 기록한 뒤 종료를 판단합니다.

백업 체크 기록: [프로젝트 / 방식 / 성공 시각 / 복구 가능 기간 / 보관 위치와 접근 / 마지막 복구 시험 / 결과 / 담당 / 미확인 사유]. 구체적인 백업 위치·실데이터·연결 문자열은 공개 저장소에 기록하지 않습니다. 목표 복구 시간·허용 데이터 손실은 담당자가 실제 백업·시험 결과에 근거해 정하며 현재는 미정입니다.
